# openwrt-sstp-tunnel

Установщик управляющего SSTP-туннеля для OpenWrt. Поднимает туннель от роутера к серверу управления и открывает из этого туннеля ровно три вещи, и только к самому роутеру:

- SSH, порт `22`
- HTTP, порт `80`
- ICMP echo-request

Больше ничего: ни доступа в LAN клиента, ни дефолтного маршрута через туннель, ни подмены DNS.

```text
Администратор / сервер управления
        │
        │ SSTP (TCP 443)
        ▼
OpenWrt-роутер клиента:  22, 80, ping
```

## Установка

```sh
wget -O - https://raw.githubusercontent.com/makxis/openwrt-sstp-tunnel/main/install.sh | sh -s install
```

Или файлом, если нужно оставить скрипт на роутере:

```sh
cd /root
wget -O install.sh https://raw.githubusercontent.com/makxis/openwrt-sstp-tunnel/main/install.sh
sh install.sh install
```

Вопросы задаются на терминале, поэтому вариант с `| sh` работает. Если терминала нет вообще (`ssh router 'sh install.sh install'`, cron), ответы читаются со stdin в том же порядке: сервер, логин, пароль, DNS.

Установщик спросит четыре вещи и дальше всё делает сам:

```text
SSTP server (host or host:port):
Username:
Password:

DNS servers the tunnel will use to resolve server.example:
  127.0.0.10 8.8.8.8 1.1.1.1
Enter to accept, 'n' for the system resolver, or type your own [y]:
```

Последний вопрос — подтверждение: Enter соглашается со списком, `n` оставляет системный резолвер, а свои адреса можно вписать через запятую или через пробел. Подробнее — [DNS для туннеля](#dns-для-туннеля).

Порт можно не указывать, тогда используется стандартный 443. Строку вида `https://server.example/` скрипт разберёт сам.

## Что происходит при установке

Проверки до того, как что-то изменено:

1. root, наличие `uci` и `ubus`, версия OpenWrt, пакетный менеджер (`opkg` или `apk`);
2. свободная память и свободное место в overlay;
3. имя сервера резолвится (`resolveip`, `nslookup` или `ping`);
4. TCP-порт сервера отвечает. Шаг пропускается, если `nc` на роутере нет вовсе или это урезанный вариант busybox без `-w` и при этом нет `timeout`.

Если сервер не резолвится, скрипт останавливается до любых изменений.

Дальше:

5. бэкап `/etc/config/network` и `/etc/config/firewall` в `/root/sstp-backup` (каталог `700`, хранятся три последних поколения). Если с прошлого раза конфиги не изменились, новая копия не пишется;
6. установка `sstp-client`, если его ещё нет, и `libopenssl-legacy`, если версии клиента нужен MD4;
7. установка своего netifd-обработчика `/lib/netifd/proto/sstpm.sh` и файла опций pppd `/etc/ppp/options.sstpm`;
8. интерфейс `network.sstp` с протоколом `sstpm`, зона firewall `sstp` и три правила;
9. hotplug `/etc/hotplug.d/iface/95-sstp-tunnel` как страховка автозапуска;
10. применение конфигурации, подъём туннеля и проверка результата.

Подъёмом считается не сам факт `"up": true`, а появление IPv4-адреса в `ifstatus`. Голый `up` приходит раньше, чем pppd договорился по IPCP, и проверка результата на нём срабатывала до того, как адрес вообще существовал.

Проверки после подъёма:

- интерфейс в состоянии `up`, ppp-устройство существует и получило IPv4;
- правило `Allow-SSH-from-SSTP` реально присутствует в живом наборе nftables или iptables;
- на портах 22 и 80 кто-то слушает (`dropbear`, `uhttpd`), иначе предупреждение.

Ошибка аутентификации и отсутствие `/etc/ppp/options.sstpm` распознаются сразу, без ожидания таймаута.

## DNS для туннеля

Отдельная опция интерфейса, `option resolvers`. Имя сервера резолвится через перечисленные в ней DNS-серверы по порядку, и только если не ответил ни один — через системный резолвер.

```
config interface 'sstp'
	option resolvers '127.0.0.10 8.8.8.8 1.1.1.1'
```

Зачем: на роутере, где DNS принадлежит чему-то вроде podkop, падение этого «чего-то» уносит с собой системный резолвер. Управляющий туннель, который не может отрезолвить свой сервер, не поднимется — ровно в тот момент, когда он и нужен, чтобы зайти и починить. Список предлагается установщиком со значением по умолчанию `127.0.0.10 8.8.8.8 1.1.1.1`: сначала локальный DNS-прокси, потом публичные. Enter соглашается, `n` оставляет только системный резолвер, свои адреса вводятся через запятую или пробел. При повторной установке подставляется то, что уже настроено на этом роутере.

Порядок важен по времени: сервер, который отказывает в соединении, стоит ноль, а тот, который молча глотает запрос, — пять секунд до сдачи `nslookup`. Поэтому локальный адрес идёт первым, публичные за ним.

Ничего в `/etc/resolv.conf`, dnsmasq или конфигурации podkop при этом не меняется: список читает только обработчик `sstpm` и только для своего интерфейса. Остальной роутер резолвит как резолвил.

Разные DNS-серверы могут вернуть разные адреса одного имени — у KeenDNS это норма. Обработчик всё равно перебирает то, что получил, по одному адресу на попытку.

## Автооткат

Перед первым перезапуском сервисов скрипт поднимает фоновый сторож. Если установщик не подтвердит успех в течение 600 секунд, сторож сам вернёт `network` и `firewall` из бэкапа и перезапустит сеть. Это страховка от потери удалённого доступа: обрыв SSH-сессии посреди установки, кривой конфиг, недоступный роутер.

Сторож снимается только после того, как туннель поднялся и прошёл все проверки. Если проверки не прошли, конфигурация возвращается из бэкапа сразу, не дожидаясь таймера.

## Два дефекта `sstp-client 1.0.20-r1`

Версия, которая лежит в 24.10 и 25.12, на OpenWrt ломается двумя независимыми способами. Скрипт лечит обе причины, а не маскирует их даунгрейдом.

### 1. Переполнение списка аргументов pppd

Это причина, по которой скрипт ставит свой обработчик протокола.

`sstp-client` складывает командную строку pppd в массив фиксированного размера (`src/sstp-pppd.c`, `sstp_pppd_start`):

```c
const char *args[20];
```

Одиннадцать слотов занимает сам `sstpc`: `pppd`, tty, скорость, `user <имя>`, `file <временный файл с паролем>`, `plugin sstp-pppd-plugin.so sstp-sock <сокет>`. Плюс завершающий `NULL`. На опции pppd остаётся ровно 8 слотов.

Штатный `/lib/netifd/proto/sstp.sh` передаёт 13, даже при выключенных `defaultroute`, `peerdns` и `ipv6`:

```text
ifname sstp-sstp require-mschap-v2 refuse-pap noauth
ip-up-script /lib/netifd/ppp-up      ipv6-up-script /lib/netifd/ppp-up
ip-down-script /lib/netifd/ppp-down  ipv6-down-script /lib/netifd/ppp-down
```

Пять указателей уезжают за границу массива. В версии `1.0.20` рядом на стеке лежит локальный буфер `speed`, его и затирает. Мусор из этого буфера уходит в pppd как аргумент, и pppd падает:

```text
pppd: unrecognized option ''
```

В версии `1.0.15` переполнение ровно такое же, просто затирает безобидное место. То есть `1.0.15` не «исправная версия», а версия, которой повезло с раскладкой стека. Баг открыт: [openwrt/packages#27318](https://github.com/openwrt/packages/issues/27318), дубль [#27324](https://github.com/openwrt/packages/issues/27324).

Поэтому скрипт ставит свой обработчик, который держит опции pppd в файлах (`/etc/ppp/options.sstpm` плюс генерируемый `/var/etc/sstpm-<интерфейс>.options`) и передаёт 2 аргумента вместо 13, независимо от настроек. Это лечит первопричину, а не симптом:

- работает и на `opkg`, и на `apk`;
- не нужно скачивать сторонний `.ipk` и делать `--force-downgrade`;
- обновление пакета `sstp-client` не стирает фикс, потому что файлы пакета не тронуты;
- штатный `/lib/netifd/proto/sstp.sh` остаётся на месте и не используется.

### 2. Нет MD4, значит нет ключей MPPE

Второй дефект коварнее, потому что в логе роутера его почти не видно. Начиная с `1.0.17` хеш пароля MS-CHAPv2 считается так (`src/sstp-chap.c`):

```c
EVP_MD_fetch(NULL, OSSL_DIGEST_NAME_MD4, "provider=legacy")
```

В OpenSSL 3 MD4 вынесен в legacy-провайдер, а в OpenWrt это отдельный пакет `libopenssl-legacy`. Без него `EVP_MD_fetch` возвращает NULL, и дальше по цепочке:

```text
sstpc: Could not create password hash     ← единственный намёк в логе роутера
  → не выведены ключи MPPE
  → не получается HLAK
  → Compound MAC в SSTP_MSG_CALL_CONNECTED неверный
```

PPP-аутентификация при этом проходит успешно, поэтому на роутере всё выглядит почти нормально, а ругается только сервер:

```text
authentication succeeded
sstp: invalid Compound MAC
→ terminated session
```

Версия `1.0.15` использовала статический `EVP_md4()` и в провайдере не нуждалась. Именно поэтому старый пин всё лечил заодно, хотя причина совсем другая.

Скрипт ставит `libopenssl-legacy` сам (около 130 КБ), если установленная версия `sstp-client` не равна `1.0.15-1` и `legacy.so` ещё нет. Пакет сам себя включает через `/etc/config/openssl`, а скрипт дополнительно проверяет, что провайдер не выключен вручную. Пакет есть во всех актуальных релизах, включая 25.12 под `apk`.

## Про версию `sstp-client 1.0.15-1`

Старые версии этого скрипта всегда и безусловно откатывали пакет до `1.0.15-1` из репозитория 23.05. Теперь пин остался только как резерв и включается сам, если туннель не поднялся, установлена не пиновая версия, и на роутере есть `opkg`. В сообщении при этом пишется, какой именно из двух дефектов виден в логе: `unrecognized option` или `could not create password hash`.

Отказ в аутентификации (`AUTH_FAILED`) резервом не считается: при неверном пароле даунгрейд не поможет, и скрипт сразу откатывает конфигурацию.

Под `apk` пин невозможен: в 25.12 лежит тот же самый `sstp-client-1.0.20-r1`, а `.ipk` из 23.05 в `apk` не установить. Зато оба лечения (свой обработчик и legacy-провайдер) работают и там.

Если пин сработал, помните: любой `opkg upgrade` вернёт `1.0.20-r1` обратно.

## Модель firewall

Зона `sstp` с закрытой политикой:

```text
input   REJECT
forward REJECT
output  REJECT
```

И три точечных разрешения: `Allow-SSH-from-SSTP`, `Allow-HTTP-from-SSTP`, `Allow-Ping-from-SSTP`. Ответные пакеты ходят по общему правилу `established,related`, так что закрытый `output` сессиям не мешает.

Доступ из туннеля в LAN клиента не открывается осознанно. Если когда-нибудь понадобится обратное, это отдельное правило `sstp → lan`, и включать его стоит только при строгой необходимости.

## Память роутера

Главный расход памяти здесь не пакет (39 КБ), а списки пакетов: `opkg update` разворачивает их в `/var/opkg-lists`, то есть в tmpfs. На роутере с 64 МБ это заметно. Что делает скрипт:

- не трогает репозитории вообще, если `sstp-client` уже установлен;
- пропускает `opkg update`, если списки свежее суток;
- перед обновлением списков проверяет свободную память и честно отказывается, если её меньше 20 МБ;
- сразу после установки удаляет `/var/opkg-lists` (или `/var/cache/apk`);
- скачивает `.ipk` только в резервном сценарии с пином и удаляет его сразу после установки.

## Статус

```sh
sh /root/install.sh status
```

Без сохранения файла на роутере:

```sh
wget -O - https://raw.githubusercontent.com/makxis/openwrt-sstp-tunnel/main/install.sh | sh -s status
```

Покажет версию `sstp-client`, наличие обработчика и файла опций, конфигурацию (пароль замаскирован), состояние интерфейса, живые правила firewall, процессы `sstpc`/`pppd` и последние строки лога.

## Удаление

```sh
sh /root/install.sh remove
```

Убираются интерфейс `network.sstp`, зона и правила, обработчик `sstpm.sh`, файл опций pppd, hotplug, а также секции от старых версий скрипта, включая маршрут к серверной LAN и правило доступа к файловому серверу, если они остались. Пакет `sstp-client` остаётся установленным, бэкапы остаются в `/root/sstp-backup`.

Полного перезапуска сети при удалении не делается: интерфейс снимается через `reload`, а зарегистрированный в памяти netifd протокол исчезнет после перезагрузки и ни на что не влияет.

## Диагностика

```sh
ifstatus sstp
logread -e sstp | tail -40
ps w | grep -E 'sstpc|pppd' | grep -v grep
ip route
nft list table inet fw4 | grep -i sstp
```

Частые случаи:

| Симптом | Что смотреть |
|---|---|
| `Could not resolve <server>` | WAN и DNS на роутере, имя сервера |
| `AUTH_FAILED` в `ifstatus` | логин и пароль, метод аутентификации на сервере |
| `unrecognized option` в логе | фикс аргументов не применился: проверьте, что в `network.sstp` стоит `proto 'sstpm'`, а не `sstp` |
| `Could not create password hash` | нет `libopenssl-legacy`, поставьте его и перезапустите туннель |
| на сервере `invalid Compound MAC` | то же самое: нет MD4, клиент посчитал криптопривязку без ключей MPPE |
| `Missing /etc/ppp/options.sstpm` | файл удалён, запустите `install` ещё раз |
| Туннель поднялся, но SSH не пускает | слушает ли `dropbear` на 22, не ограничен ли он интерфейсом |

## Требования и совместимость

- OpenWrt 23.05 и 24.10 (`opkg`), 25.12 (`apk`);
- доступ в интернет с роутера;
- рабочий SSTP-сервер и корректные логин с паролем;
- `ppp` и `resolveip` в системе, они приходят зависимостями `sstp-client`;
- около 1 МБ свободного overlay, если ничего из нужного ещё не стоит.

Замер на чистой 24.10.3 (Huasifei WH3000 Pro), где не было ни одного из пакетов: overlay вырос на 988 КБ. Из них `sstp-client` 273 КБ, `libevent2-7` 260 КБ, `libopenssl-legacy` 133 КБ, `resolveip` 64 КБ, `libopenssl-conf` 19 КБ, остальное — служебные файлы `opkg`. Сам скрипт добавляет 10 КБ (обработчик, опции pppd, hotplug) и по 23 КБ на комплект бэкапов. Поднятый туннель занимает около 7 МБ RAM: `sstpc` 6 МБ, `pppd` 1,1 МБ.

На роутере, где `libevent2` и openssl-обвязка уже есть, расход заметно меньше — порядка 500 КБ.

## Безопасность

Пароль туннеля неизбежно лежит открытым текстом в `/etc/config/network`, поэтому скрипт ставит на этот файл права `600`. Бэкапы содержат тот же пароль и лежат в каталоге `700`. Ввод пароля при установке идёт без эха и не попадает в историю shell.

Обработчик запускает `sstpc` с `--cert-warn`, как и штатный обработчик OpenWrt: ошибки сертификата сервера становятся предупреждением, а не отказом. Если нужна строгая проверка, добавьте `--ca-cert` в опции и уберите `--cert-warn`:

```sh
uci set network.sstp.sstp_options='--tls-ext --ca-cert /etc/ssl/my-ca.pem'
uci commit network
ifdown sstp; ifup sstp
```

Опция `--tls-ext` включена по умолчанию, она передаёт имя хоста в TLS (SNI) и нужна, если сервер стоит за reverse proxy или делит адрес с другими сайтами.
